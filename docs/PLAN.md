## 2. 技术栈

### 选定：TypeScript 全栈 + Three.js 3D（网页）

核心原则：**逻辑是 2D 的，画面是 3D 的**。模拟核心只算平面坐标 (x, y)、朝向和高度层（水面/水下/空中），Three.js 只负责把它画出来。这样 3D 不会让游戏逻辑变复杂，也不影响以后做联机。

| 层 | 选型 | 理由 |
|---|---|---|
| 语言 | TypeScript（严格模式） | 客户端、服务端、数据工具、AI 共用一套代码 |
| 包管理 / 运行时 | pnpm workspace + Node 24（本机已装） | monorepo 拆包；Bun 可用于跑脚本 |
| 渲染 | **Three.js**，用 `WebGPURenderer`（浏览器不支持 WebGPU 时自动退回 WebGL2），着色器用 TSL 写 | 网页上能做出不错的 3D 效果；TSL 写一次，两种后端都能跑 |
| 镜头 | 魔兽式 RTS 镜头：固定俯角透视、滚轮缩放、边缘/拖拽平移 | 还原原版视角；点击地图时对水平面做射线检测，不对模型做检测，开销小 |
| 地形与海面 | 用 `w3e` 高度和地表数据生成岛屿网格；海面是一张大平面 + 自定义水面着色器（Gerstner 波浪、浅滩泡沫、反射） | 海面占满整屏，是最影响观感的部分，值得专门做 |
| 模型 | glTF/GLB 低多边形风格船只；用 `InstancedMesh` 画炮弹、NPC 小艇和装饰物 | 风格化低模美术成本可控，实例化渲染让上千个弹道保持流畅 |
| 特效 | three.quarks 粒子（炮口火光、爆炸、水花、技能），尾迹用自定义条带网格 | 技能特效是 BOOM 的观感重点 |
| 3D 写法 | **直接用 Three.js，不用 React Three Fiber** | 几百个实体每帧更新，自己管渲染循环更直接、更容易调性能 |
| UI | React + Zustand（只做 HUD、商店、计分板），以 DOM 层叠在画布上 | 游戏画面归 Three.js，菜单面板归 React，两者互不干扰 |
| 构建 | Vite | 开发热更新快 |
| 游戏模拟 | 自研纯 TS 模拟核心，固定 20 tick/秒，与渲染完全分离 | 和魔兽一样的 tick 制；可在 Node 里无头运行，用来跑 AI 自我对战和平衡测试，日后直接当联机服务器 |
| 寻路 | 基于 `wpm` 的网格：A* 求全局路径 + 流场给 NPC 舰队 + 简单避让 | 地图通行数据现成；舰船按尺寸（小/中/大/巨大）分别算通行 |
| 数据校验 | zod schema → 生成 JSON | 地图数据进游戏前先校验，防止解析错误 |
| 数据提取 | Python（mpyq 读 MPQ）或 TS 脚本，放 `tools/` | 一次性管线，产物提交进仓库 |
| 测试 | Vitest（模拟核心单测）+ Playwright（冒烟测试） | 模拟核心是纯函数，好测 |
| 联机（后期） | Node + WebSocket（`ws`），服务端权威 + 客户端插值 | 10 人以内的对局，权威服务器比帧同步简单得多，也不用追求浮点确定性 |
| 打包桌面版（可选） | Tauri | Web 版跑通后，套壳成本很低 |

### 备选方案对比

| 方案 | 优点 | 缺点 | 判断 |
|---|---|---|---|
| **TS + Three.js（选定）** | 网页即玩、3D 效果好、模拟核心可直接复用到服务器 | 需要 3D 模型，美术工作量比 2D 大；要自己搭镜头、地形、海面 | 用逻辑与画面分离 + 低多边形风格控制成本 |
| TS + PixiJS 2D | 开发最快、美术最便宜 | 观感弱 | 已放弃 |
| Babylon.js | 自带物理、GUI、编辑器，更像"引擎" | 包体大，社区案例和生态不如 Three.js | 可行，但 Three.js 资料更多 |
| Godot 4 / Unity | 编辑器完整 | 网页导出包体大、启动慢；联机要另做服务端 | 不推荐 |

### 美术方案：AI 生成

所有美术资源都用 AI 生成。三种 3D 建模方式各有所长，**按资源类型分工，而不是只选一种**：

| 方式 | 擅长 | 不擅长 | 用在哪里 |
|---|---|---|---|
| **生图模型 → Tripo 图生 3D** | 造型复杂、有机的物体：龙头船首、龟船船壳、亡者之船、海怪；自带贴图 | 细长结构（桅杆、绳索、薄帆）容易糊成一团；网格面数高、拓扑乱；贴图里常带光影；阵营色难改 | **31 艘船的船体**、海怪/虎鲸/多头蛇等生物、特殊建筑 |
| **AI 写 Blender Python 脚本**（`bpy`，可配合 Blender MCP） | 规则的硬表面物体，尺寸精确、可批量改；以及**批量清理和导出** | 从零建复杂有机造型效果差 | 基地、炮台、船厂、港口、码头等模块化建筑；**所有模型的统一后处理** |
| **AI 直接写 Three.js 程序化几何** | 需要参数化或动画的东西：随风鼓起的帆、旗帜、炮弹、水雷、龙卷风、护盾、冰冻罩 | 精细静态模型 | 占位船、帆和阵营旗、弹道、技能特效的几何体 |

**船的组合方式**：船体用 Tripo 生成；桅杆、帆、阵营旗由 Three.js 程序化生成，挂到船体预留的挂点上。这样既避开了 Tripo 做细长结构的短板，帆能动，阵营色（南方/北方）也能直接换色。

另外，**2D 图标的量比 3D 模型还大**：31 艘船、47 种武器、116 种物品、约 100 个技能，共约 300 个图标。直接用生图模型出图，最适合 AI 来做。

#### 生产流水线（全部脚本化）

```
assets/manifest.json            每个资源一条：id、类型、提示词、参考图、种子、状态、选中的候选
   │
   ├─ 1. 概念图   生图模型，用统一的风格模板 + 风格参考图；
   │             船出侧视、3/4 视角各一张，纯色背景、无光影
   ├─ 2. 图生 3D  Tripo API，每个资源出 3–4 个候选，人工挑一个
   ├─ 3. 后处理   Blender 无头模式运行（blender -b -P process.py）：
   │             统一朝向和比例、原点放在吃水线、减面到预算、
   │             标出桅杆挂点和炮口位置、导出 GLB
   ├─ 4. 优化     glTF-Transform：Meshopt 压缩网格、KTX2 压缩贴图
   ├─ 5. 校验     自动检查面数、包围盒尺寸、朝向、贴图大小
   └─ 6. 预览页   Three.js 资源浏览页：所有船并排转盘展示、对比大小、切换阵营色
```

本机条件：已装 Blender（`/Applications/Blender.app`，命令行未加入 PATH）；M1 Max 32GB。混元 3D、TRELLIS 等开源图生 3D 模型基本需要 NVIDIA 显卡，本机跑不动，所以用 Tripo 等云端服务。

#### 风格统一

AI 生成最大的问题是 31 艘船风格不一致。对策：

- 先定**风格手册**：例如"风格化低多边形 + 手绘质感贴图、偏卡通的比例、限定调色板"，再写一份固定的提示词模板。
- 先生成 3–5 张满意的图作为**风格参考图**，之后每次出图都带上。
- 生图模型和 Tripo 的版本在整个项目里固定，不中途更换。
- 在预览页里把所有船放在一起看，不合群的重做。

#### 美术规范（M1 定下来）

一个游戏单位等于多少米、船的朝向轴、面数上限（小船约 1–2 千面，巨大战舰约 5–8 千面）、贴图尺寸（小船 512，大船 1024）、挂点命名规则。每艘船只要一个低模 + 一张贴图，不需要骨骼动画，摇晃和沉没都用代码做。

#### 版权

- 魔兽 3 的模型、图标、音效属于暴雪；地图内容属于作者刀锋战士。自己玩没问题，公开发布前船名和技能名最好征得作者同意或改名。
- 提示词里不要写"魔兽""暴雪"或具体作品名，生成的设计要是原创的。
- 有几艘船本身取材于别人的作品：**黄金美丽**（《海贼王》梅利号）、**黑珍珠**和**飞行的荷兰人**（《加勒比海盗》）。公开发布时这几艘需要重新设计外形并改名。
- AI 服务的商用条款要在选定时确认：很多服务的免费档生成的资源不能商用或必须署名，付费档才给商用授权。条款会变，以开始批量生产时官网的说明为准。

## 3. 代码结构

```
BOOM_BattleShips/
├─ data/                    # 原始地图和已解析表（只读）
├─ tools/extract/           # 地图解析脚本：SLK、j 脚本、w3e、wpm、doo → JSON
├─ tools/art/               # AI 美术流水线：生图、Tripo 调用、Blender 后处理脚本、优化与校验
├─ packages/
│  ├─ gamedata/             # 解析后的 JSON + zod schema + 类型
│  ├─ sim/                  # 模拟核心：实体、移动、武器、伤害、技能、Buff、经济、出兵、胜负
│  ├─ ai/                   # 电脑玩家
│  ├─ client/               # Three.js 渲染（镜头、地形、海面、模型、特效）+ React HUD + 输入
│  ├─ assets/               # GLB 模型、贴图、音效（可整体替换）
│  └─ server/               # （后期）联机服务器，复用 sim
└─ docs/
   ├─ PLAN.md               # 本文件
   └─ mechanics/            # 从 j 脚本整理出的规则说明（出兵、经济、每个技能）
```

模拟核心关键约定：

- 数据驱动：船、武器、物品、技能都从 `gamedata` 读，代码里不写死数值。
- 武器随机索敌：每把武器独立冷却，在射程内、符合攻击对象类型的敌人中随机挑一个（原版机制）。
- 伤害公式按魔兽 3：护甲减伤 = 0.06×护甲 / (1 + 0.06×护甲)，另外处理"船甲减伤"和"无视船甲"。
- 技能 = 通用框架（无目标/点目标/单位目标/被动/光环 + Buff 系统：定身、沉默、减速、眩晕、隐形、护盾）+ 少数特殊技能单独写脚本。
- 随机数统一走带种子的 RNG，便于复现 bug 和回放。

> - 无头跑 20 分钟纯 NPC 对局只需 9.8 秒（平均每 tick 0.4 ms）。
>
> - 规则细节：修理站（一次修一艘，修理中无敌且不能动，修满自动离港，Esc 或按钮提前离开）；快速模式关闭西侧航道、一方全灭时开放 120 秒；每 15 分钟全局科技（防御火力、船只火力、舰船耐久、船只提速，按单位数据里的科技列表生效）；NPC 击沉玩家后升级（+300 耐久、致命一击、+15 回复、+15% 攻速）；复活后 5 秒无敌；`?mode=standard` 切换联赛标准模式。

## 5. 主要风险

| 风险 | 对策 |
|---|---|
| j 脚本里技能逻辑是触发器写的，读懂费时 | M0 先列触发器→技能对照表；每个技能先按 SLK 数值用通用框架实现，特殊效果再补 |
| 魔兽内置技能（如冻结、隐形）没有源码，只有数值 | 按魔兽公开行为文档复刻，必要时开魔兽对比实测 |
| 寻路性能（几十艘 NPC 船） | NPC 用共享流场，玩家用 A* |
| "大船转向慢"的手感 | M1 专门调转向和惯性参数，并对照原版录像 |
| AI 生成的模型风格不统一、质量参差 | 风格手册 + 固定参考图 + 固定模型版本；每个资源多出几个候选；预览页并排审看 |
| Tripo 输出的网格面数高、拓扑乱、贴图带光影 | Blender 脚本统一减面和清理；提示词要求无光影的平光贴图；实在不行用 Tripo 自带的低模/重拓扑选项 |
| AI 服务涨价、改条款或停服 | 流水线每一步都可以换供应商；生成结果（概念图、原始模型）全部存档 |
| 团战时画面卡顿（10 名玩家 + NPC 舰队 + 大量炮弹和技能特效） | 炮弹和小船用实例化渲染；粒子设上限；M2 起就在性能面板里盯帧率和绘制调用数 |
| WebGPU 在部分浏览器/显卡上不可用或有兼容问题 | `WebGPURenderer` 自动退回 WebGL2，每个里程碑在两种后端上都测一次 |
| 首次加载慢 | 模型和贴图压缩、按需加载船只模型 |
| 版权 | 素材可替换；公开发布前换美术、联系作者 |
